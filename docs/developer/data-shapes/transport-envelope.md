# Transport Envelope (apiHandler)

All frontend-to-backend API calls are routed through `apiHandler` in
`src/backend/z_Api/z_apiHandler.js`. The handler wraps every response in
a stable envelope. Contract files in this folder document only the `data`
payload inside this envelope.

## Success envelope

```typescript
{
  ok: true,
  requestId: string,    // UUID generated by Utilities.getUuid()
  data: unknown,        // Handler-specific payload (or null when undefined)
}
```

- `data` is coerced from `undefined` to `null` via `data ?? null` as a
  defensive measure to prevent Zod parsing errors on the frontend.
- `requestId` is a V4 UUID produced by `Utilities.getUuid()` (GAS native).
- The envelope never contains a `meta` field in the backend response, but
  the frontend `ApiSuccessResponseSchema` tolerates an optional `meta`
  field for forward compatibility.

## Error envelope

```typescript
{
  ok: false,
  requestId: string,
  error: {
    code: string,         // One of: 'RATE_LIMITED' | 'INVALID_REQUEST' |
                          //         'UNKNOWN_METHOD' | 'IN_USE' |
                          //         'DEFINITION_STALE' | 'INTERNAL_ERROR'
    message: string,      // Human-readable error string
    retriable?: boolean,  // true for RATE_LIMITED; omitted otherwise
    details?: object,     // Structured metadata (e.g. for DEFINITION_STALE:
                          //   { definitionKey, referenceStale, templateStale,
                          //     referenceLastModified, templateLastModified })
  },
}
```

### Error code mapping

| Error type                  | Code               | retriable |
| --------------------------- | ------------------ | --------- |
| `ApiRateLimitError`         | `RATE_LIMITED`     | `true`    |
| `ApiValidationError`        | `INVALID_REQUEST`  | `false`   |
| `ApiDisabledError`          | `UNKNOWN_METHOD`   | `false`   |
| `DefinitionStaleError`      | `DEFINITION_STALE` | `false`   |
| `error.reason === 'IN_USE'` | `IN_USE`           | `false`   |
| Any other error             | `INTERNAL_ERROR`   | `false`   |

For `DEFINITION_STALE`, the error envelope includes a `details` block with
`definitionKey`, `referenceStale`, `templateStale`, `referenceLastModified`,
and `templateLastModified`.

## Envelope validation (frontend)

The frontend validates the envelope in `src/frontend/src/services/apiService.ts`
using `ApiResponseSchema` (a `z.discriminatedUnion('ok', [...])`):

```typescript
// ApiSuccessResponseSchema
z.object({
  ok: z.literal(true),
  requestId: z.string(),
  data: z.unknown(), // Validated further by feature schema
  meta: z.record(z.string(), z.unknown()).optional(),
}).superRefine((response, ctx) => {
  /* data field must exist */
});

// ApiErrorResponseSchema
z.object({
  ok: z.literal(false),
  requestId: z.string(),
  error: z.object({
    code: z.string(),
    message: z.string(),
    retriable: z.boolean().optional(),
  }),
  meta: z.record(z.string(), z.unknown()).optional(),
});
```

## Key contract notes

- **Date serialisation:** `google.script.run` prohibits `Date` objects in
  return values. Each API handler that returns nested Date objects must
  call `DateUtils.deepConvertDates(response)` before returning. This is
  done per-handler, not in `apiHandler`, to avoid the performance cost on
  endpoints that do not need it.
- **Defensive null coercion:** `_success()` maps `undefined` to `null` to
  prevent Zod `.nullable()` schema errors on the frontend.
- **Handler failures** are caught by `apiHandler`, logged with the original
  thrown error, then mapped to the frontend-safe envelope contract without
  exposing raw exception details.
- **Request validation** checks `request.method` is a non-empty string and
  `request.params` is optional. Handlers validate their own parameters.
