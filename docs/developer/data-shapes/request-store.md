# Contract: RequestStore

Internal API request tracking store persisted via GAS PropertiesService. Tracks the lifecycle
of each API request from admission (started) through completion (success or error). Used by
`ApiDispatcher` in `z_apiHandler.js` for rate limiting, active-request accounting, and
diagnostic tracing.

Backend implementation: `src/backend/z_Api/requestStore.js`
Constants: `src/backend/z_Api/apiConstants.js`
Persistence: `PropertiesService.getUserProperties()` under `USER_REQUEST_STORE_KEY`
API handlers: Not directly callable — consumed internally by `ApiDispatcher` in `z_apiHandler.js`

Sibling contracts:

- [Contract: BackendConfig](backend-config.md) — Shares GAS PropertiesService persistence
  pattern (`getUserProperties()` vs `getScriptProperties()`).
- No other sibling contracts — RequestStore is an internal backend mechanism with no
  frontend-facing transport, no API endpoints, and no registration in
  `ALLOWLISTED_METHOD_HANDLERS`.

### Store shape

The store is a JSON-serialised object stored under `USER_REQUEST_STORE_KEY` (value: `'AB_USER_REQUEST_STORE'`)
in GAS User Properties. Each key is a `requestId` string (V4 UUID), each value is a record:

| Field          | Type     | Required | Notes                                                                                           |
| -------------- | -------- | -------- | ----------------------------------------------------------------------------------------------- |
| `requestId`    | `string` | yes      | UUID generated by `Utilities.getUuid()`                                                         |
| `method`       | `string` | yes      | API method name from `ALLOWLISTED_METHOD_HANDLERS` (e.g. `'getABClassPartials'`)                |
| `status`       | `string` | yes      | One of: `'started'`, `'success'`, `'error'`                                                     |
| `startedAtMs`  | `number` | yes      | Epoch timestamp in milliseconds                                                                 |
| `finishedAtMs` | `number` | no       | Set by `markSuccess_()` / `markError_()` — present only when status is `'success'` or `'error'` |
| `errorMessage` | `string` | no       | Set by `markError_()` — present only when status is `'error'`                                   |

### Record lifecycle

The store is managed by seven functions in `requestStore.js`. Lifecycle steps are
orchestrated by `ApiDispatcher` in `z_apiHandler.js`:

1. **`createStartedRecord_(requestId, method, startedAtMs?)`** — Pure factory function.
   Returns a new record with `status: 'started'` and the given (or current) timestamp.
   Validates `requestId` and `method` via `Validate.requireParams`; validates `startedAtMs`
   is a finite number. Does not read or write to PropertiesService.

2. **`loadStore_()`** — Reads the JSON blob from `PropertiesService.getUserProperties()`.
   Returns `{}` when:
   - The stored value is `null` (no prior store exists).
   - `JSON.parse` throws (malformed data).
   - The parsed value is `null`, not a plain object, or is an array.
     Logs a warning via `ABLogger` for the latter two cases.

3. **`saveStore_(store)`** — Serialises the store object to JSON and writes it to
   `PropertiesService.getUserProperties()`. Validates `store` via `Validate.requireParams`.

4. **`markSuccess_(store, requestId)`** — Sets `status` to `'success'` and `finishedAtMs` to
   `Date.now()` on the record identified by `requestId`. Mutates and returns the store.
   Validates `store` and `requestId` via `Validate.requireParams`.

5. **`markError_(store, requestId, errorMessage)`** — Sets `status` to `'error'`,
   `finishedAtMs` to `Date.now()`, and `errorMessage` to the provided string on the record
   identified by `requestId`. Mutates and returns the store. Validates `store`, `requestId`,
   and `errorMessage` via `Validate.requireParams`.

6. **`pruneStaleEntries_(store, stalenessThresholdMs, referenceTimeMs?)`** — Removes entries
   whose `status` is `'started'` and whose `startedAtMs` is older than `referenceTimeMs -
stalenessThresholdMs`. Completed entries (`'success'` / `'error'`) are never removed by
   this function. Mutates and returns the store. Validates `store` and `stalenessThresholdMs`
   via `Validate.requireParams`; validates `referenceTimeMs` is a finite number.

7. **`compactStore_(store)`** — When the total number of entries exceeds `MAX_TRACKED_REQUESTS`,
   removes the oldest completed entries (sorted by `startedAtMs` ascending) until the store
   fits within the limit. Active (`'started'`) entries are always preserved. Mutates and
   returns the compacted store. Validates `store` via `Validate.requireParams`.

### Constants

Defined in `src/backend/z_Api/apiConstants.js`:

| Constant                      | Value                     | Notes                                                                   |
| ----------------------------- | ------------------------- | ----------------------------------------------------------------------- |
| `USER_REQUEST_STORE_KEY`      | `'AB_USER_REQUEST_STORE'` | PropertiesService key for the store                                     |
| `MAX_TRACKED_REQUESTS`        | `30`                      | Maximum entries before `compactStore_()` evicts oldest                  |
| `ACTIVE_LIMIT`                | `25`                      | Maximum concurrent `'started'` entries before new requests are rejected |
| `STALE_REQUEST_AGE_MS`        | `900000` (15 min)         | `ACTIVE_REQUEST_STALE_MINUTES` (15) × 60 × 1000                         |
| `LOCK_TIMEOUT_MS`             | `1000`                    | Lock acquisition timeout in milliseconds                                |
| `LOCK_WAIT_WARN_THRESHOLD_MS` | `300`                     | Lock wait duration above which a warning is logged                      |

### Key persistence notes

- The store is loaded at the start of `ApiDispatcher._runAdmissionPhase()` and saved
  immediately after pruning stale entries. It is loaded again in
  `ApiDispatcher._runCompletionPhase()`, mutated (mark + compact), and saved.
- `loadStore_()` is defensive: it returns `{}` when the stored value is `null`, unparseable,
  or not a plain object. Warnings are logged for invalid data.
- `saveStore_()` callers are responsible for compaction — `_runCompletionPhase()` calls
  `requestStoreFns.saveStore_(requestStoreFns.compactStore_(store))` to ensure the store does
  not grow unbounded.
- There is no frontend Zod schema — this is an internal backend-only store with no transport
  endpoints.
- The store key uses `'AB_USER_REQUEST_STORE'` (prefixed with `AB_`) to avoid collisions
  with other GAS scripts sharing the user's property store.
- `ACTIVE_LIMIT` (25) is slightly lower than `MAX_TRACKED_REQUESTS` (30), ensuring there is
  headroom for completed entries alongside active ones without triggering compaction on
  every request.

### Admission-phase usage in `ApiDispatcher`

```
_runAdmissionPhase(requestId, method):
  1. Acquire user lock (LockService.getUserLock().tryLock(1000ms))
  2. store = loadStore_()
  3. pruneStaleEntries_(store, STALE_REQUEST_AGE_MS, lockAcquiredAt)
  4. saveStore_(store)                              // persist pruned state immediately
  5. count active entries; if >= ACTIVE_LIMIT → reject with RATE_LIMITED
  6. store[requestId] = createStartedRecord_(requestId, method, lockAcquiredAt)
  7. saveStore_(store)
  8. Release lock
```

### Completion-phase usage in `ApiDispatcher`

```
_runCompletionPhase(requestId, method, handlerFailed, handlerError):
  1. Acquire user lock (LockService.getUserLock().tryLock(1000ms))
  2. store = loadStore_()
  3. if handlerFailed → markError_(store, requestId, String(handlerError))
     else → markSuccess_(store, requestId)
  4. saveStore_(compactStore_(store))
  5. Release lock
```

## Transport

This store has no API endpoint transport. It is an internal backend mechanism consumed
exclusively by `ApiDispatcher.handle()` in `z_apiHandler.js`. There is no `z_Api` handler
file, no `ALLOWLISTED_METHOD_HANDLERS` registration, and no frontend service or Zod schema
for this store.

The store's data does appear indirectly in the transport envelope's `requestId` field
(see [Transport Envelope](transport-envelope.md)), but the store itself is never serialised
into any endpoint response payload.

## Validation

**Backend validation** (all in `src/backend/z_Api/requestStore.js`):

- `createStartedRecord_()`: validates `requestId` and `method` via `Validate.requireParams`.
  Validates that `startedAtMs` is a finite number via `Validate.isNumber()`.
- `saveStore_()`: validates `store` via `Validate.requireParams`.
- `markSuccess_()`: validates `store` and `requestId` via `Validate.requireParams`.
- `markError_()`: validates `store`, `requestId`, and `errorMessage` via `Validate.requireParams`.
- `compactStore_()`: validates `store` via `Validate.requireParams`.
- `pruneStaleEntries_()`: validates `store` and `stalenessThresholdMs` via `Validate.requireParams`.
  Validates that `referenceTimeMs` is a finite number via `Validate.isNumber()`.

**Key domain rules:**

- `compactStore_()` always preserves active (`'started'`) entries. Only completed entries are
  evicted when the store exceeds `MAX_TRACKED_REQUESTS`. This ensures in-flight requests are
  never lost from tracking.
- `pruneStaleEntries_()` only removes `'started'` entries older than the staleness threshold.
  Completed entries are never pruned — they are only removed by `compactStore_()`.
- The admission phase enforces an `ACTIVE_LIMIT` (25) on concurrent `'started'` entries.
  If the limit is reached, new requests receive a `RATE_LIMITED` failure envelope and are
  never dispatched to their handler.
- When `markError_()` is called, `errorMessage` is set to `String(handlerError)`, converting
  the thrown value to a string regardless of its original type. This is a defensive
  serialisation to guarantee a string value in the store.
- The `_runCompletionPhase()` acquires a lock separately from the admission phase. If the
  completion lock cannot be acquired, a warning is logged but the overall request response
  is still returned to the caller. The request just won't be tracked as completed.

### Known discrepancies

1. **No frontend visibility of the store.** The RequestStore is purely internal to the
   backend. There is no frontend Zod schema, no API endpoint to query the store, and no
   mechanism to surface store contents in the UI. This is intentional — the store is a
   backend-internal rate-limiting and diagnostic mechanism.
   **Classification: Aligned** — deliberate design choice.

2. **`markSuccess_()` and `markError_()` do not verify the record exists before mutating.**
   Both functions access `store[requestId]` without checking for the record's presence. If
   a `requestId` is not in the store (e.g. because the store was concurrently replaced or
   pruned), the mutation will throw a `TypeError` (`Cannot set properties of undefined`)
   when attempting to set `store[requestId].status`. This is a latent fragility — a
   missing-record guard would provide a more informative failure.
   **Classification: Fragile** — a missing-record guard could prevent a TypeError from
   propagating to the error envelope.

3. **`loadStore_()` returns `{}` for non-object types but does not surface this via error
   envelope.** Malformed or unexpected store data is silently reset. Warnings are logged
   via `ABLogger`, but no alerting or structured error is propagated. This is intentional
   for a self-healing internal store.
   **Classification: Aligned** — deliberate self-healing design.
