# 🚀 v0.7.9

This release adds application-level authentication with role-based access control. The existing
Google Group gate is retained as one of two selectable providers, and a new Script Properties
provider lets you authorise named users without a Google Group. A fresh install is claimed by the
first interactive caller as the sole administrator, and administrators manage the provider from a
new Authentication tab in Settings.

## ✨ Enhancements

- **Two-provider authentication model.** `authMode` selects between `googleGroups` (Google Group
  membership, cached for six hours) and `scriptProperties` (a stored user list, read fresh on
  every call). The removed `'none'` mode is rejected fail-closed by the strict resolver.
- **Role-based access control.** The auth layer now resolves an `admin` or `user` role and
  delivers it to the frontend. The new Authentication tab in Settings is visible only to admins.
- **Fresh-install bootstrap claim.** On a genuinely fresh install, the first eligible interactive
  caller becomes the sole administrator through an atomic, lock-guarded claim. Trigger execution
  and blank identities never claim.
- **Authentication settings UI.** The admin-only Authentication tab supports provider selection,
  a staged user table (Script Properties), the compulsory-once-set group email (Google Groups),
  and a single atomic Save with revision guarding.
- **Management endpoints.** `getApplicationAccess` (gate-exempt, performs the bootstrap claim),
  `getAuthenticationSettings` (admin-only), and `setAuthenticationSettings` (admin-only, atomic
  revision-guarded save) replace the previous ad-hoc configuration path. The ordinary backend
  configuration transport rejects the auth-managed fields for every caller.

## 🔐 Authentication rollout

### Manual seed for the Script Properties provider

All application configuration lives in a single JSON blob stored under the Script Properties key
`__CONFIG_STORE_KEY__` — there are no separate per-field keys. If the UI is unreachable (for
example after a misconfiguration that locks out all admins), you seed the `scriptProperties`
provider by editing that one key and pasting the entire blob below, exactly as written.

**Exact literal value for `__CONFIG_STORE_KEY__`:**

```json
{
  "authMode": "scriptProperties",
  "authGroupEmail": "",
  "authUsers": "[{\"email\":\"admin@example.com\",\"role\":\"admin\"}]",
  "authRevision": "1"
}
```

**Double serialisation is required.** `authUsers` is stored as a JSON **string**, not a native
array. In the blob above it appears as `"[{\"email\":\"admin@example.com\",\"role\":\"admin\"}]"`
— a JSON string whose content is itself a JSON array. The two layers of serialisation are
intentional and mirror what the API writes: the bootstrap claim stores
`JSON.stringify([{ email, role: 'admin' }])` as the `authUsers` value, and `validateAuthUsersJson_`
parses that string back into an array. Paste the escaped value **exactly** as shown; do not
"helpfully" un-escape it to the raw array form `[{"email":"admin@example.com","role":"admin"}]`
(that makes `authUsers` a native JSON array rather than the required JSON string, and the strict
resolver rejects it), and do not escape it a second time (that produces an invalid string and also
yields a `brokenConfig` denial).

**Malformed or double-incorrect seed → `brokenConfig` deny.** If `authUsers` is not a valid JSON
string, parses to a list with zero admins, or `authRevision` is missing or invalid, the strict
resolver (`validateAuthStateStrict_`) throws and every protected call returns a `brokenConfig`
denial with an error-level audit. The application fails closed; it never grants access from a
half-written seed. To recover, correct the `__CONFIG_STORE_KEY__` value or clear the blob entirely
so the fresh-install bootstrap claim can run again.

### Deploy order

The `apiAuth` transport shapes and the dispatcher's admin-status admission phase form one locked
contract and shipped together in ACTION_PLAN Section 5. The backend-configuration `.strict()`
lockstep is a separate, later dependency: Section 6 drops the auth fields from the
`getBackendConfig` read transport and Section 7 drops them from the frontend `BackendConfig` Zod
schemas, so those two surfaces must ship together in the same release. The builder deploys the
whole backend bundle (and the frontend) through a single `clasp` push, so none of these surfaces
are ever split. Do not attempt a partial backend or frontend deploy; a half-deployed surface would
send or receive mismatched shapes and could admit or deny incorrectly.

## 🗂 Files changed (high level)

- `src/backend/Utils/AuthService.js`, `GoogleGroupsAuthService.js`, `ScriptPropertiesAuthService.js`
  — the two-provider singleton, the bootstrap claim, and the management domain operations.
- `src/backend/z_Api/apiAuth.js` — the three authentication transport endpoints.
- `src/backend/z_Api/apiConfig.js` — auth-managed fields rejected from the ordinary config write.
- `src/backend/z_Api/z_apiHandler.js` — gate-exempt and admin-required admission handling.
- `src/frontend/src/features/auth/AppAuthGate.tsx` — warm-up driven by `getApplicationAccess`,
  role delivery via context.
- `src/frontend/src/features/settings/authentication/AuthenticationSettingsTab.tsx` — the
  admin-only Authentication tab.
- `docs/developer/security/application-authentication.md`, `accepted-risks.md`, and
  `docs/developer/data-shapes/auth-users.md` — updated to describe the two-provider model.

## ⬆️ Updating to v0.7.9

1. Open the Admin Sheet and choose Assessment Bot → Settings → Update Version.
2. Select v0.7.9 from the dropdown and follow the prompts to reinstall the latest script bundle.
3. On a fresh install, the first interactive caller becomes the sole administrator automatically;
   configure the provider promptly after updating.

## 🧾 Changelog summary (technical)

- Feature: two-provider application authentication (`googleGroups` / `scriptProperties`) with
  role-based access control and a fresh-install bootstrap claim.
- Feature: admin-only Authentication tab with provider selection, staged user management, and
  atomic revision-guarded save.
- Change: authentication state is managed only through the dedicated endpoints; the ordinary
  backend-configuration transport rejects the auth-managed fields for every caller.
- Docs: `application-authentication.md` and `accepted-risks.md` updated for the two-provider
  model, manual-seed recovery, and the deploy-order contract.
