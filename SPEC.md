# ProgressTracker API Polling Specification

## Status

- Draft v1.1
- Revised after independent review. Scope remains backend plus frontend API surface only.

## Purpose

This document defines the behaviour for exposing backend progress state to the React frontend through the existing `apiHandler` transport.

The feature will be used to:

- give each assessment run a progress record keyed by the `requestId` generated for its `startAssessmentRun` API call;
- let the frontend retrieve all active run progress records in one API call, ready for later polling;
- keep per-run writes isolated so parallel runs do not overwrite one another;
- remove finished progress records with a single deferred cleanup trigger per user, rather than scanning all keys on every write or poll.

This feature is **not** intended to:

- create or change any UI component, modal, page, or polling hook;
- change how assessment scoring, persistence, or feedback works;
- replace the existing API transport envelope or rate-limiting mechanism;
- introduce a second frontend-to-backend transport.

## Agreed product decisions

1. The `requestId` generated by `ApiDispatcher.handle()` is the correlation key. It is passed into `startAssessmentRun`, stored in trigger context, supplied to `processSelectedAssignment`, and returned in the `startAssessmentRun` response `data` so the frontend can record it.
2. `startAssessmentRun` response `data` changes from `null` to `{ requestId: string }`. The backend envelope is unchanged.
3. A new allowlisted `getProgress` method returns all keyed progress records in one payload. It takes no parameters and needs a response schema only.
4. Each progress record is stored under a separate User Property key derived from its `requestId`. The legacy unkeyed `ProgressTracker` key is retained only for calls that have no run context.
5. `getProgress` returns only keyed records (those with a non-empty `requestId`). The legacy unkeyed record is internal and is not exposed to the frontend.
6. Cleanup uses one pending time-based trigger per user, scheduled 10 minutes after a progress write when no cleanup trigger is already pending. The pending state is held in a per-user cache entry with a per-user User Property marker as the authoritative fallback. Both are cleared and re-established atomically after each cleanup run.
7. The cleanup trigger deletes only terminal progress records (`completed: true` or a non-null `error`). If any non-terminal record remains, it re-arms one further cleanup trigger 10 minutes later. It never deletes a record whose run may still be in flight.
8. Frontend delivery in this task is the API surface only: a typed service wrapper and Zod schemas. Polling scheduling and hooks are out of scope.
9. No new trigger-based cleanup is exposed as a frontend-callable API method; it runs only through the existing `triggerHandler` entry point.
10. The dispatch request ID is exposed to handlers through a request-scoped accessor owned by `ApiDispatcher`, not by adding a positional argument to every handler.
11. Cleanup state is per user because progress records live in per-user User Properties under `USER_ACCESSING` execution.

## Assumptions

- A progress record represents one assessment **run**, not a coursework task. The agreed transport field name remains `tasks`.
- The cleanup marker and cache flag are user-scoped so one teacher's pending trigger cannot suppress another teacher's cleanup.
- The web app continues to execute as `USER_ACCESSING` with `DOMAIN` access; no manifest change is required.

## Existing system constraints

### Backend or API constraints already in place

- `apiHandler` in `src/backend/z_Api/z_apiHandler.js` is the sole frontend transport. All callable methods must be registered in `ALLOWLISTED_METHOD_HANDLERS`.
- `ApiDispatcher.handle()` generates `requestId` with `Utilities.getUuid()`, measures admission/completion with `LockService.getUserLock()`, and tracks requests in the User Property store documented by `request-store.md`.
- `startAssessmentRun` does not run the assessment. It validates inputs, checks definition freshness, and schedules a time-based `triggerHandler` trigger with context stored in Script Properties (`trigger-context.md`). The progress-tracked work runs later in `processSelectedAssignment`.
- `TriggerController.createTimeBasedTrigger(functionName, triggerTime)` already accepts an explicit `Date`. Its generic error handling calls `removeTriggers()` for quota errors (which deletes unrelated `triggerHandler` triggers) and `logAndThrowError()` for all other errors (which would re-arm cleanup through `logError`). The method is extended with an options object carrying `skipTooManyTriggersRecovery`; when that option is true, **any** trigger-creation error is logged via `ABLogger` and the method returns `null`. It never calls `removeTriggers()`, `logAndThrowError()` or any scheduler, and leaves the marker/cache unset for a later progress write. Existing callers keep the default behaviour.
- `triggerHandler` is the single public trigger entry point. Trigger methods must be registered as anonymous arrow functions in `TRIGGER_METHOD_HANDLERS` and receive context resolved from Script Properties.
- All `PropertiesService` access must go through `GASPropertiesUtils`. `CacheManager` is the shared cache wrapper and requires an explicit TTL; it currently wraps `CacheService.getScriptCache()`.
- `ProgressTracker` is a `BaseSingleton`; callers use `getInstance()`. It holds an in-memory `step` counter and currently writes to a single `ProgressTracker` User Property.
- `getCurrentProgress()` is read by `BaseRequestManager` and `LLMRequestManager` to build incremental progress messages. `getStatus()` and `getStepAsNumber()` are legacy methods used only by tests.
- `Validate.requireParams()` rejects only `null`/`undefined` and accepts empty strings; `Validate.validateNonEmptyString()` is the correct validator for `requestId`.
- Top-level backend functions must carry a trailing underscore; frontend-callable handlers are anonymous closures in the allowlist. A guarded `module.exports` block is required for Node tests. The static global-exposure guard enforces this boundary.

### Current data-shape constraints

- The success envelope is `{ ok: true, requestId: string, data: unknown }` returned as a JSON string; `data` is coerced from `undefined` to `null`.
- `google.script.run` forbids `Date`, `Function` and DOM values. Progress records therefore use ISO 8601 strings for timestamps.
- `StartAssessmentRunResponseSchema` is currently `z.void().nullable()` because the handler returns `null`.
- User Property storage is capped at 9 KB per value and 500 KB per property store; property read/write quota is 50,000/day for consumer accounts and 500,000/day for Workspace accounts.

### Frontend or consumer architecture constraints

- All frontend calls go through `callApi`, which returns parsed `data` only and discards the envelope `requestId`.
- Every backend method has a small service module with adjacent Zod schemas; void responses use `.nullable()`.
- Polling hooks belong under `src/frontend/src/features/`, not in pages or services. This task adds no such hook.

## Domain and contract recommendations

### Why this approach is preferable

- Keying by the existing dispatch `requestId` avoids inventing a second identifier and keeps frontend correlation aligned with backend logging.
- Per-run properties avoid the read-modify-write contention of a single shared progress blob. Reading them for a status poll is one `getProperties()` call, not one call per run.
- A single deferred cleanup trigger per user avoids scanning and rewriting every progress key on each write or poll, and keeps cleanup outside the request path.
- Terminal-only deletion with re-arming cannot remove a record while its GAS execution may still be running (executions are capped at 6 minutes).
- A per-user marker prevents one user's trigger from suppressing another user's cleanup.

### Recommended data shapes

#### Progress record (User Property value)

```ts
{
  requestId: string; // Non-empty; matches the dispatch requestId
  step: number; // Finite, monotonic within the run
  message: string; // User-facing progress text
  completed: boolean; // True only once the run has finished successfully
  error: string | null; // User-facing error text, null when absent
  timestamp: string; // ISO 8601 UTC string from the last write
}
```

#### `getProgress` response `data`

```ts
{
  tasks: ProgressRecord[]; // Sorted by timestamp ascending, then requestId ascending
}
```

#### `startAssessmentRun` response `data`

```ts
{
  requestId: string; // Same value as the envelope requestId
}
```

### Naming recommendation

Prefer:

- `requestId`
- `tasks`
- `getProgress`
- `ProgressTracker<requestId>` for keyed User Properties

Avoid:

- `progressId` or `runId` (a second identity would need its own correlation rules)
- `status` as a payload field name (it conflicts with the envelope's boolean `ok`)

### Validation recommendation

#### Frontend

- `ProgressRecordSchema` requires non-empty `requestId`, finite `step`, string `message`, boolean `completed`, `error` as `z.string().nullable()` and `timestamp` as `z.iso.datetime()` (canonical UTC `Z` form emitted by `toISOString()`).
- `StartAssessmentRunResponseSchema` requires `{ requestId: z.string().min(1) }` and is not nullable, because the handler always returns an object.
- `GetProgressResponseSchema` requires `{ tasks: ProgressRecord[] }` and accepts an empty array.

#### Backend

- The dispatcher validates `requestId` is a non-empty string before storing it in the request context.
- `processSelectedAssignment` validates `requestId` with `Validate.validateNonEmptyString()`, not `requireParams()`.
- `getProgress_` takes no parameters and performs no request validation beyond the dispatcher envelope.
- Cleanup skips malformed keyed records with a logged warning rather than aborting the whole sweep; it does not rewrite them.

### Display-resolution recommendation

- The frontend matches a record to a started run by `requestId` only. It must not infer identity from `step`, `message` or ordering.
- Records with `completed: true` or a non-null `error` are terminal; all other records are in flight.

## Feature architecture

### Placement — contractual ownership boundaries

- `ProgressTracker` remains the sole owner of progress state, the active run context, and cleanup coordination.
- The dispatcher owns the request-scoped `requestId` accessor; handlers read it and do not receive a new positional argument.
- `TriggerController` owns trigger creation and context storage; the cleanup coordinator decides when to call it and uses the `skipTooManyTriggersRecovery` option so a full trigger quota cannot delete assessment triggers. The facade split separates keyed persistence from cleanup scheduling because they have distinct owners and test surfaces, not because of a line-count threshold.
- `getProgress_` is a trailing-underscore helper in a single `z_Api` module, registered through `ALLOWLISTED_METHOD_HANDLERS`.
- The cleanup method is an anonymous arrow entry in `TRIGGER_METHOD_HANDLERS`; no new public GAS function is introduced.
- The frontend service for `getProgress` lives in the existing `assignmentAssessment` service domain with an adjacent response schema.

Detailed file placement is an implementation concern; canonical data-shape documents record the planned helper owners.

### Out of scope for this surface

- Any polling interval, hook, timer, `useEffect` or rendered progress indicator.
- Changes to `ApiResponseSchema` or to `callApi`'s return contract.
- Changes to the assessment pipeline beyond passing `requestId` through existing parameters.

## Data loading and orchestration

### Required datasets or dependencies

- `requestId` from `ApiDispatcher.handle()`.
- Trigger context keys `trigger:<uid>:method` and `trigger:<uid>:params`.
- User Property keys matching `ProgressTracker<requestId>`.
- A per-user User Property marker for the pending cleanup trigger and a matching user-cache flag.

### Prefetch or initialisation policy

- No progress data is prefetched. `ProgressTracker` keeps its lazy `ensureInitialized()` boundary.
- `startAssessmentRun` returns the correlation ID synchronously; no progress record is fetched at that point.
- `getProgress` returns the current snapshot when called by a later frontend consumer.
- No manual refresh or polling control exists in this task.

### Query or transport additions

- `getProgress` is registered in `ALLOWLISTED_METHOD_HANDLERS`.
- No cache or query key is added to the frontend in this task.

## Core view model or behavioural model

### Suggested shape

```ts
type ProgressRecord = {
  requestId: string;
  step: number;
  message: string;
  completed: boolean;
  error: string | null;
  timestamp: string;
};
```

### Derivation or merge rules

#### In-flight

- `completed === false` and `error === null`.

#### Completed

- `completed === true`; `error` remains `null`.

#### Failed

- `error !== null`; `completed` remains `false`.

#### Legacy unkeyed

- Stored under `ProgressTracker` with no `requestId`; used by call sites with no active run context and excluded from `getProgress`.

### Sort order or priority rules

1. `getProgress` sorts by `timestamp` ascending, then `requestId` ascending as a deterministic tie-break.
2. The legacy unkeyed record is never included in the returned array.

## Workflow specification

## Request-scoped request ID

### Behaviour

- `ApiDispatcher.handle()` sets the accessor immediately after generating `requestId`, before the auth gate and handler call.
- The accessor exposes `set(requestId)`, `get()` and `resetForTests()`; it is owned by `z_apiHandler.js` and is not a public GAS function.
- Every call to `handle()` overwrites the stored value, so no cross-call cleanup is needed inside a single GAS execution. Tests call `resetForTests()` between cases.
- Methods other than `startAssessmentRun` may read the accessor but must not depend on it.

## Start an assessment run

### Eligible inputs or preconditions

- Existing validated `definitionKey`, `assignmentId`, `courseId`, as today.

### Behaviour

- `startAssessmentRun_` reads the accessor and passes the `requestId` to `AssignmentController.startAssessmentRun()` and back in the response data.
- `startProcessing()` stores `{ assignmentId, definitionKey, courseId, requestId }` in the trigger context.
- `processSelectedAssignment()` validates the new field with `Validate.validateNonEmptyString()` and calls `startTracking(requestId)`.
- `startTracking(requestId?)` binds the active run context when an ID is supplied; with no ID it uses the legacy unkeyed key. Every later write in that execution targets the bound record.
- With an active context, `getCurrentProgress()` reads the keyed record; with none it reads the legacy record. `getStatus()` and `getStepAsNumber()` follow the same rule.
- `complete()` writes the terminal record through the still-bound context and only then clears it. Clearing first would send the terminal write to the legacy key and leave the keyed record non-terminal forever. The context is also cleared by `resetForTests()`. On `logAndThrowError()` the execution ends with the context still bound, which is harmless because each GAS execution has its own singleton instance.
- `ProgressTracker` must not set `FREEZE_AFTER_INIT`, because the active context is mutated after `ensureInitialized()`.

### Failure rule

- A missing or empty `requestId` in trigger params fails loudly with `Validate.validateNonEmptyString()`; the run does not start with an unkeyed record.

## Retrieve progress

### Eligible inputs or preconditions

- None beyond the normal `apiHandler` admission and auth gates.

### Behaviour

- `getProgress_` reads all User Properties, filters keys with the `ProgressTracker` prefix and a non-empty `requestId`, parses them, sorts them and returns `{ tasks }`.
- The handler is a trailing-underscore function with a guarded `module.exports` block for tests.

### Failure rule

- A malformed keyed record is logged as a warning and skipped; other records are still returned. A failure to read the property store propagates to the `apiHandler` error boundary.

## Schedule and run cleanup

### Eligible inputs or preconditions

- A keyed or legacy progress write has occurred.

### Behaviour

- On a write, the coordinator checks the cached flag; on a cache miss it reads the per-user marker. If neither is present, it acquires `LockService.getUserLock()`, rechecks, creates one trigger via `TriggerController.createTimeBasedTrigger('triggerHandler', new Date(now + 10 minutes), { skipTooManyTriggersRecovery: true })`, stores context `{ method: 'cleanupProgress', params: {} }`, writes the marker and sets the cache flag.
- The cache flag TTL is 600 seconds, defined in the cleanup module. `CacheManager.put()` receives it explicitly. The durable marker, not the cache, guarantees correctness when the flag expires.
- Further writes do not create another trigger while the flag or marker is present.
- The cache wrapper is extended so the coordinator can use `getUserCache()` and remove a key; the shared wrapper keeps its existing script-cache behaviour for other consumers.
- Trigger creation passes `{ skipTooManyTriggersRecovery: true }`. If the quota is exhausted, `createTimeBasedTrigger()` logs a warning and returns `null`; the coordinator leaves the marker and cache flag unset so a later write retries. It must not call `TriggerController.removeTriggers()`, which would delete assessment triggers.
- When the trigger fires, `triggerHandler` resolves context, authorises and dispatches `cleanupProgress`.
- Cleanup deletes only terminal progress records. On a successful sweep it clears the cache flag and marker and, if any non-terminal record was observed, re-arms one trigger and rewrites the marker and cache flag for the new trigger UID before returning. `triggerHandler` deletes the fired trigger and its context in its own `finally` block.

### Failure rule

- A sweep failure clears the cache flag and marker in a `finally` block and does **not** re-arm, then propagates to `triggerHandler`. `triggerHandler` calls `logAndThrowError(error.message, error, { deferCleanup: true })`; `logError` accepts an optional `deferCleanup` flag and skips `schedule()` when it is true. This prevents the error-logging path from immediately re-arming the trigger it just failed to clean up. The next ordinary progress write re-arms. Re-arming happens only after a successful sweep that actually observed a non-terminal record.
- Any trigger-creation failure under `skipTooManyTriggersRecovery` (quota or otherwise) is logged by `createTimeBasedTrigger()` and returns `null`. It leaves the marker and cache flag unset, never deletes a `triggerHandler` trigger, never calls `logAndThrowError()` or `schedule()`, and retries only on a later ordinary progress write.
- Lock acquisition failure on scheduling logs a warning and does not create a duplicate trigger; progress writes still succeed.

## Error, loading, and empty-state rules

### Blocking failure

- Failure to obtain the User Property store or to write a progress record propagates to the caller. No error is swallowed.

### Partial-load failure

- A malformed keyed record is skipped with a warning; other records are still returned.

### Empty state

- When no keyed records exist, `getProgress` returns `{ tasks: [] }`.

### Legacy fallback

- Unkeyed progress writes continue to work for existing call sites. They are stored under `ProgressTracker`, are not returned by `getProgress`, and are eligible for terminal cleanup.

## Backend changes required to support agreed behaviour

1. Add the request-scoped accessor to `ApiDispatcher` and return the correlation ID from `startAssessmentRun`.
2. Refactor `ProgressTracker` into a facade with separate keyed-store and cleanup modules.
   - Preserve `getInstance()`, `resetForTests()`, `getCurrentProgress()`, `getStatus()` and `getStepAsNumber()`.
   - Extend `logError()` and `logAndThrowError()` with an optional options object carrying `deferCleanup`; default behaviour is unchanged for all existing callers. `captureError()` stays unchanged.
   - Bind and clear the active context as specified; use `GASPropertiesUtils` for all property access.
3. Add the `getProgress_` transport helper, registration and guarded exports.
4. Add the `cleanupProgress` trigger method, user-scoped cache flag and durable marker.
5. Extend `CacheManager` to support a supplied cache instance and key removal.

## Frontend changes required to support agreed behaviour

1. Change `StartAssessmentRunResponseSchema` to `{ requestId: z.string().min(1) }` (non-nullable).
2. Change `startAssessmentRun()` from `Promise<null>` with an `as null` cast to `Promise<StartAssessmentRunResponse>` with no cast.
3. Add `getProgress()` to the `assignmentAssessment` service domain with a response schema only.

No UI components, hooks, timers or polling loops are added.

## Scope

### In scope

- Correlation ID plumbing through the dispatcher, `startAssessmentRun`, trigger context and `processSelectedAssignment`.
- Keyed User Property storage with a legacy fallback and active run context.
- `getProgress` backend handler and registration.
- Frontend service wrapper and Zod schemas, including the changed start response.
- Deferred cleanup trigger with user-scoped cache-backed dedupe and terminal-only deletion with re-arm.
- Canonical documentation and tests.

### Deferred

- Frontend polling scheduler and hook (explicitly excluded from this task).
- Any UI display of progress.
- Replacing the legacy unkeyed record used by non-run call sites.
- Extending the transport envelope to expose `requestId` to all `callApi` consumers.
